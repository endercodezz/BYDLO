# Руководство по ручному тестированию

## Редактор профиля (#9)

`ProfileEditTests` проверяет сохранение имени, адреса, параметров и выбранного движка,
сохранность метаданных, независимость черновика и откат при ошибке записи.
`ServerWizardTests` проверяет ручной ввод OpenVPN и недопустимые учётные данные.
Проверки `BundledEngineTests` используют только `FakeProcessRunner`: файл авторизации
содержит две строки, секреты не передаются в аргументах, временные файлы удаляются
при остановке и ошибке. Реальные процессы и сетевые настройки не используются.

```powershell
. ./scripts/env.ps1
dotnet run --project tools/Bydlo.Screenshots -c Release -- .tmp/profile-editor-ui ru --mock --verify-wizard
```

Используйте новый каталог вывода. Headless-сценарий проверяет ручной OpenVPN,
маскирование и раскрытие секретов, сохранение учётных данных, очистку формы,
а также изменение имени и адреса через настоящий диалог редактора. Скриншоты
мастера создаются для широкого и узкого окна. Реальное подключение OpenVPN
с `auth-user-pass` проверяет только мейнтейнер вручную.

[Инструкция по редактору](PROFILE_EDITOR.md).

## Привилегированная служба (#83)

Изолированные проверки протокола, политик, целостности и владения сессией входят в
`PrivilegedHelperTests` и выполняются через `scripts/check.ps1` / `scripts/check.sh`
при `BYDLO_SAFE_DEV=1`, без сервера IPC, служб и реальных движков.
Установку/удаление и работу без повышенных прав мейнтейнер проверяет вручную по
[отдельному руководству](PRIVILEGED_HELPER.md#проверки). На Windows, Linux и macOS
эти проверки ещё не выполнены; Mock Mode не подтверждает работоспособность службы.

## Мастер добавления серверов (#6)

Безопасная автоматическая проверка после загрузки `scripts/env.ps1` / `scripts/env.sh`:
`dotnet run --project tools/Bydlo.Screenshots -c Release -- .tmp/wizard-verification ru --verify-wizard --mock`.
Используются отдельный каталог данных, поддельный HTTP-обработчик и тестовый буфер обмена;
движки не запускаются, запросы в реальную сеть не отправляются.

Проверяются три карточки, выбор протокола, предпросмотр без записи, отмена и возврат,
base64 со смешанными корректными/некорректными строками, файлы, QR-картинка и скриншот
из буфера, загрузка подписки с метаданными и сохранение без повторного запроса,
ошибка HTTP без утечки токена, отмена загрузки, ручная форма и отсутствие автоподключения.
Скриншоты на русском сохраняются для обычного и узкого окна.

Для #137 сценарий также выбирает тип импорта в форме: один и тот же HTTP(S)-адрес
со стандартным или нестандартным портом импортируется как прокси без HTTP-запросов
и как подписка через фиктивный HTTP-обработчик. Проверяются TLS и порт прокси,
отсутствие записи при предпросмотре, сохранение связи с подпиской без повторной
загрузки, возврат с предпросмотра и сброс выбора при завершении мастера.

`ServerWizardTests` проверяют валидацию ручной формы и хранение ключей отдельно от
профилей, необязательные метаданные подписки, сохранение её связей и откат записи
профилей/секретов при ошибке файлового хранилища.

Ручная проверка в Mock Mode: открыть мастер кнопкой на главной и в «Подключениях»,
пройти все три карточки через системные диалоги и настоящий drag-and-drop,
проверить Escape, Tab и обычную вставку текста. При отмене файлы настроек и список
серверов не меняются; «Добавить» сохраняет серверы без запуска подключения.


## Резервная копия (#18)

`BackupTests` проверяют шифрование всего архива, отсутствие открытых секретов, случайность
шифротекста, неверный пароль, повреждение файла, сохранение связей с подписками,
объединение/замену, сохранение локальных настроек устройства и откат при ошибках записи.
Используются временные файлы и `InMemorySecretStore`; сетевые запросы и движки не запускаются.

Проверка интерфейса в изолированном headless-сеансе (после `scripts/env.ps1` или `scripts/env.sh`):
`dotnet run --project tools/Bydlo.Screenshots -c Release -- .tmp/backup-verification ru --verify-backup --mock`.
Проверяются маски паролей, привязка кнопки применения, переключение режима, отмена,
применение замены и обновление страниц. Скриншоты сохраняются для обычной и узкой ширины.
Используются поддельные ключи; Mock Mode и safety lock включены явно.

При ручной проверке с отдельными тестовыми данными экспортируйте копию через системный диалог,
откройте её с неверным, затем с верным паролем. Убедитесь, что до подтверждения ничего
не меняется, отмена предпросмотра оставляет данные на месте, а оба режима импорта
совпадают с предпросмотром. Полный формат и ограничения описаны в [BACKUP.md](BACKUP.md).

## Встроенные движки (#29)

Безопасная проверка сборщика: загрузить `scripts/env.ps1`, выполнить `scripts/check.ps1`,
затем оба упаковщика из `BUILD.md` и
`scripts/verify-engine-bundle.ps1 -Rid <rid> -PublishDirectory <каталог>`.
Последняя команда только читает файлы: проверяет наличие движков, PE/ELF/Mach-O архитектуру,
комплект DCO и SHA-256. CI на GitHub проверяет так все пять RID;
зеркало на Gitea — только Linux x64, его результат не подтверждает остальные RID.
Для Windows ARM64 отсутствие
Zapret не должно прерывать упаковку sing-box/Xray/AmneziaWG/OpenVPN.

`BundledEngineTests` используют поддельные процессы, DNS и сетевые службы: проверяют приоритет
встроенных копий, UAPI и секреты AmneziaWG, запрет `.conf`-хуков, отдельные маршруты и DNS,
журнал/повторную очистку и запрет установки драйвера при safety lock. Ни один движок не запускается.

Headless-проверка интерфейса на фиктивных данных, без установки DCO:

```powershell
. ./scripts/env.ps1
dotnet run --project tools/Bydlo.Screenshots -c Release -- .tmp/bundle-verification ru --mock --verify-bundled-engines
```

Для статической сверки запуска проверьте общий `SystemProcessRunner`: оба пути (`Start` и
`RunToCompletionAsync`) используют `UseShellExecute=false`, `CreateNoWindow=true` и
перенаправление потоков. Адаптеры должны передавать ему бинарники, а не GUI или BAT-файлы.
Это проверка кода; видимость окон в реальной ОС подтверждается только вручную.

Только владелец вручную на отдельной тестовой машине с обычным запуском:

1. Распаковать релиз без клиентов Amnezia/OpenVPN, убрать доступ к GitHub. Убедиться, что движки
   найдены локально и подключение не требует загрузки. Проверить каждую доступную ОС/архитектуру.
2. AmneziaWG: импортировать `.conf`, подключить с повышенными правами; проверить адреса, IPv4/IPv6,
   DNS, доступность сервера и mesh-сетей. Отключить — выделенный адаптер и временные маршруты исчезают.
3. Прервать процесс BYDLO; процесс-хост должен завершиться по закрытию stdin/смерти родителя.
   После следующего запуска с повышенными правами проверить восстановление по `amnezia-network.json`.
   Ошибка очистки должна оставлять журнал для повторной попытки, не менять чужие адаптеры.
4. Windows OpenVPN: без согласия ничего не устанавливается. В «Инструменты → Движки» поставить
   флажок, явно запустить установку DCO от администратора; проверить подпись драйвера и адаптер
   `BYDLO-OpenVPN`. При отказе UAC/установки — понятная ошибка; BYDLO не перезагружает ОС автоматически.
5. Подключить DCO-совместимый TUN-профиль. Отключить — OpenVPN получает штатный Windows exit event
   (Unix — SIGTERM), убирает маршруты. GUI, консольные окна и службы OpenVPN не появляются.
   Драйвер/адаптер остаются в системе, как указано до установки. TAP и устаревшие DCO-несовместимые
   параметры не заявлены поддерживаемыми на Windows.
6. Для каждого доступного движка проверить запуск, повторное подключение и остановку:
   отдельные окна, консоль и иконки движков в панели задач/трее не появляются.
   TgWsProxy работает внутри BYDLO. Системный запрос повышения прав не является окном движка.
7. Проверить комплект `LICENSE`, `THIRD_PARTY_NOTICES.md`, `engines/licenses/`,
   `engines/sources/`, lock-файлов и `ENGINES-SHA256SUMS.txt`; сверить компоненты с
   «Настройки → О программе». После переноса всей папки движки находятся без повторной загрузки.

Эти сценарии выполняет мейнтейнер вручную; агент их не запускает. Упаковка и модульные тесты сами по себе не подтверждают реальные подключения.

Автоматические тесты в репозитории **изолированы**: они никогда не запускают движки, не открывают туннели и не меняют
системные сетевые настройки. Всё, что описано ниже, должен проверить человек на машине, где потеря связи допустима
(лучше всего на виртуальной машине или отдельном устройстве). **Не выполняйте эти шаги на машине, удалённый доступ к
которой зависит от её текущих сетевых настроек.**

Запускайте BYDLO из оболочки **без** `BYDLO_SAFE_DEV` (или используйте сборку из CI). Для отчётов об ошибках сохраняйте
`logs/bydlo.log` (путь к каталогу данных показан в Настройки → Дополнительно). Учётные данные из лога уже вырезаны, но
перед отправкой всё равно проверьте его.

## 0. Mock-режим (безопасно где угодно)

1. `dotnet run --project src/Bydlo.Desktop -- --mock`.
2. Подключения → *Демо-серверы (mock)*. Главная → Подключить: статус меняется «Подключение…» → «Подключено», таймер и скорость обновляются.
3. Настройки → Дополнительно → сценарий Mock = *Ошибка при подключении*: появляется баннер с ошибкой.
4. Сценарий = *Сбой через ~20 с*: статус становится «Переподключение…», затем снова «Подключено» (автопереподключение).
5. Включите Zapret / TgWsProxy на главной: оба показывают «Работает» независимо от туннеля.
6. Переключите темы (светлая / чёрная / системная; фиолетовая — в пользовательских темах) и язык (RU / EN); сузьте окно до ширины меньше 760 px — появится нижняя навигация.

### Проверка интерфейса без сетевых движков

Проверка уведомления о новой версии (#119) с подменённым HTTP входит в `StartupUpdateCheckerTests`
и `UpdateCheckerTests`: отключённая проверка, текущая версия, черновики и предварительные релизы,
повторный запуск с сохранённым уведомлением, суточный интервал и недоступность GitHub.
Неудачная попытка тоже учитывается в суточном интервале. Найденный релиз сохраняется до закрытия
уведомления или успешного открытия страницы; после установки этой версии уведомление удаляется.
Загрузка и установка выполняются пользователем на странице релиза.

Безопасная проверка баннера в Mock Mode (приветствие, обычная и узкая ширина, закрытие,
сохранение после исчезновения другого уведомления) со скриншотами:

```powershell
. ./scripts/env.ps1
dotnet run --project tools/Bydlo.Screenshots -c Release -- .tmp/update-notification ru --verify-updates
```

Для полного обновления галереи README в PowerShell запустите:

```text
./scripts/update-screenshots.ps1
```

Скрипт включает Mock Mode и Safe Dev, использует новый каталог данных внутри `.tmp`,
обновляет все снимки и ссылки README. Имя каждого PNG включает SHA-256 содержимого:
новая картинка получает новый URL, а прежние снимки заменяются. Это не даёт браузеру
или GitHub повторно использовать старый адрес изображения для нового интерфейса.
После сборки можно использовать `./scripts/update-screenshots.ps1 -NoBuild`.
Для отдельных временных рендеров доступен `dotnet run --project tools/Bydlo.Screenshots -c Release -- .tmp/screenshots ru`.
Снимки охватывают все пять разделов на десктопе и при ширине 400 px, три темы,
подключённое состояние и ошибку, Home при 380 px и границу переключения навигации 760 px.
Генератор также проверяет переключение режимов через реальные элементы Home, открытие и закрытие секции и отображение ошибки Mock.
Проверяйте читаемость подписей, перенос строк, доступность кнопки подключения и отсутствие
перекрытий нижней навигацией. Для клавиатурной проверки в Mock Mode пройдите Tab / Shift+Tab:
фокус должен быть виден на кнопках, полях, выборе темы и навигации.

## 1. Движки

- В полном релизе откройте «Инструменты → Движки»: sing-box и Xray должны иметь статус «Готов»
  без скачивания и установки. Сохраняйте всю папку `engines` при переносе приложения.
- Отдельно проверьте запасную загрузку при отсутствии встроенной копии. Проверка подмены:
  в отдельном checkout измените хеш в `engines/engines.lock.json`, пересоберите и установите —
  установка должна завершиться ошибкой целостности и ничего не оставить.

## 2. Режим локального прокси (без прав администратора)

Для каждого протокола, для которого у вас есть сервер (VLESS/REALITY, VLESS XHTTP, VMess, Trojan, SS, Hysteria 2, TUIC, SOCKS, WireGuard через sing-box):

1. Импортируйте через буфер обмена, файл и изображение с QR-кодом.
2. Подключитесь. Настройте браузер на SOCKS5 `127.0.0.1:2080`, откройте сайт проверки IP — IP должен быть адресом сервера.
3. В «Статистике» видна скорость в реальном времени (sing-box) или пометка «движок пока не сообщает трафик» (Xray).
4. Отключитесь — порт 2080 закрыт. Завершите процесс движка вручную во время подключения — появятся попытки переподключения.
5. Займите порт 2080 другой программой — подключение должно быть отклонено с понятным сообщением.
6. Серверы → *Проверить задержку*: у каждого сервера появляется замер, недоступные помечены; включите сортировку по задержке. Главная → *Лучший сервер*: выбирается сервер с минимальной задержкой и начинается подключение. Для UDP-протоколов замер приблизительный.
7. Доступ из LAN: Настройки → Дополнительно → *Доступ из локальной сети*: без логина и пароля опция не включается. Нельзя сочетать с системным прокси. Включите с логином и паролем, подключитесь — с другого устройства в сети прокси доступен только с авторизацией. Отключите опцию — порт снова слушает только 127.0.0.1. Правила фаервола BYDLO не меняет.

## 3. Режим TUN (администратор/root)

1. Настройки → Перезапустить от администратора (Windows) или запустите через sudo (Linux/macOS).
2. Главная → включите TUN, подключитесь. Все приложения идут через туннель; роутер и принтер в локальной сети доступны (если включён обход локальных сетей).
3. При включённом «Mesh-VPN диапазоны — напрямую» уже работающая mesh-VPN (например, Tailscale, ZeroTier, NetBird) продолжает работать.
4. Отключитесь — маршрут по умолчанию и DNS возвращаются в исходное состояние.
5. Без прав root на Linux/macOS в «Настройки → Дополнительно» вместо кнопки перезапуска видно пояснение про ручной запуск с root; кнопка перезапуска доступна только на Windows.

## 4. Нативные WireGuard / AmneziaWG / OpenVPN

1. Только для нативного WireGuard установите официальный клиент (`wireguard.exe` / `wg-quick`).
   AmneziaWG на Windows/Linux и OpenVPN используют полный комплект BYDLO без официального клиента;
   для Windows OpenVPN сначала выполните явную установку встроенного DCO, описанную выше.
   Импортируйте `.conf` / `.ovpn`. Подключитесь с правами администратора/root.
2. Windows: только нативный WireGuard создаёт службу туннеля `WireGuardTunnel$bydlo-wg`,
   после отключения она удаляется. Встроенные AmneziaWG/OpenVPN работают отдельными
   процессами без служб официальных клиентов; их очистку проверяйте по разделу #29 выше.
3. Профили OpenVPN с `auth-user-pass` без сохранённых учётных данных должны показывать понятную ошибку (редактор учётных данных — в roadmap).

## 5. Zapret (проверяет только мейнтейнер)

1. Распакуйте официальный релиз Windows x64 и запустите с правами администратора. Нажмите Zapret на главной без захода в «Инструменты»: встроенная копия и `general.bat` должны выбираться автоматически. Проверьте также запуск без доступа к GitHub. Загрузка закреплённого релиза и папка пользователя остаются резервными вариантами.
2. Убедитесь, что не запущены другие `winws.exe` или GoodbyeDPI (иначе BYDLO откажется стартовать).
3. Выберите `general`, нажмите «Запустить». В логах вывод winws, статус «Работает». Проверьте Discord / YouTube.
4. Отредактируйте пользовательские списки, сохраните, перезапустите Zapret. Попробуйте другие стратегии и игровой фильтр.
5. Остановите — `winws.exe` завершён. Закройте BYDLO во время работы — при следующем запуске BYDLO предложит остановить оставшийся процесс.

### Linux / macOS и восстановление правил

1. Используйте отдельную VM со снимком. На Linux установите nftables, проверьте NFQUEUE; на macOS проверьте стандартные `com.apple/*` filter/rdr anchors и отсутствие слушателя TCP 21771. Запускайте BYDLO с root, но проверяйте трафик macOS от обычного пользователя.
2. Без ручной установки движка включите Zapret: Linux запускает nfqws, macOS — tpws. На Linux проверьте TCP/QUIC и оба пресета; на macOS — только IPv4 TCP 80/443. UDP, IPv6 и трафик root на macOS должны остаться без изменений.
3. До и после остановки сравните правила системы: появляется и удаляется только `inet bydlo_<id>` (Linux) или `com.apple/bydlo_<id>` (macOS). Общие таблицы, политики, чужие anchors и состояние PF других клиентов не должны меняться.
4. Завершите только дочерний движок: BYDLO должен снять правила до публикации ошибки/переподключения. Проверьте отмену запуска и ошибку применения правил. На Linux `queue bypass` пропускает трафик при отсутствии слушателя.
5. Принудительно завершите BYDLO. При следующем запуске **того же каталога данных** с root вне Mock/Safe Dev BYDLO снимает записанные правила; оставшийся процесс движка показывается отдельно в `ProcessJournal`. Без root очистка откладывается; не считайте её выполненной. Это восстановление при следующем запуске, не watchdog после SIGKILL.
6. При ошибке очистки `<data>/zapret/firewall.json` сохраняется для повтора. Не удаляйте журнал до ручной проверки. PF использует reference token (`-E`/`-X`), никогда `pfctl -d` и не заменяет корневой ruleset. Между получением PF-токена и его записью возможен сбой питания: anchor будет снят при восстановлении, но reference может потребовать ручного разбора; автоматическое глобальное выключение PF недопустимо.
7. Измените все три пользовательских списка, обновите/переустановите приложение и управляемую копию — записи в `<data>/zapret/lists` должны сохраниться. Старые списки из папки Flowseal мигрируют только при отсутствии целевого файла.

### Антивирус / карантин (Windows)

WinDivert может определяться как RiskTool/PUA. BYDLO проверяет наличие `winws.exe`, `WinDivert.dll`, `WinDivert64.sys`, `cygwin1.dll` и списков; при пропаже показывает сообщение о карантине/восстановлении, а не статус готовности. Сверьте источник релиза и `SHA256SUMS.txt`, изучите детали детекта в антивирусе и документацию upstream. Не отключайте защиту автоматически; BYDLO не добавляет исключения и не восстанавливает карантин. Для разработки достаточно сборки и тестов с фейками, скачивать бинарники на рабочую машину не требуется.

## 6. TgWsProxy

Последний полный прогон шагов 1–10: Windows x64, мейнтейнер — всё работает.

1. Убедитесь, что Python не нужен: в Инструменты → TgWsProxy → Дополнительно написано «Встроенный движок».
2. Включите «Прокси Telegram» на главной или в инструментах. Когда прокси заработает, нажмите
   кнопку с бумажным самолётом и подтвердите подключение в Telegram. Повторное нажатие
   открывает то же окно. Чтобы остановить прокси, выключите переключатель. Если Telegram
   не установлен, приложение предлагает скопировать ссылку.
3. «Новый секрет» — ссылка меняется, появляется сообщение о необходимости перезапуска.
4. Займите порт 1443 — запуск должен быть отклонён с сообщением о конфликте порта.
5. Фото и видео грузятся; в логах (включите «Подробные логи») видны `WS pool hit` для DC из списка DC → IP и
   `trying CF proxy` для остальных DC.
6. Отключите «Резервный путь через Cloudflare» — DC вне списка идут через `TCP fallback`.
7. Укажите домен Fake TLS, обновите прокси в Telegram по новой ссылке (`ee…`) — подключение работает; в логе есть
   `Fake TLS profile`. Открытие `https://127.0.0.1:1443` в браузере перенаправляет на этот домен.
8. Статистика трафика TgWsProxy меняется во время загрузки медиа.
9. Оставьте Telegram без дела на 3–5 минут, затем откройте чат и медиа: всё грузится сразу, без задержки на

10. Отправьте компьютер в сон и разбудите: TgWsProxy остаётся «Работает» и продолжает обслуживать Telegram. Если в логе

## 7. Системный прокси (Windows)

Включите Настройки → Дополнительно → *Включать системный прокси при подключении*, подключитесь в режиме локального прокси:
настройки прокси Windows указывают на 127.0.0.1:2080. Отключитесь (а также закройте BYDLO во время подключения) — прежние
настройки прокси восстанавливаются.

При аварийном завершении восстановление выполняется при следующем запуске с тем же каталогом данных.
До первой записи в реестр BYDLO атомарно сохраняет журнал `windows-system-proxy.json`: прежние и применяемые
значения, включая отсутствие параметров и типы строк. Восстанавливаются только значения, совпадающие с записанными BYDLO.
Если другое приложение сменило адрес прокси, его адрес и флаг включения сохраняются. При ошибке записи или уведомления
WinINet журнал остаётся для следующей попытки восстановления.

Безопасная автоматическая проверка: `WindowsProxyRecoveryTests` использует только фиктивный реестр и временные файлы.
Она покрывает новый экземпляр после аварии, частичную запись и восстановление, сторонние изменения, недоступный журнал,
ошибку уведомления и блокировку параллельного экземпляра. Реальный реестр и сетевые настройки тесты не затрагивают.

## 8. Проверка соединения

1. Подключитесь в режиме локального прокси (sing-box или Xray).
2. Главная → *Проверить соединение*: появляется карточка с внешним IP, страной и задержкой. IP должен быть адресом
   сервера, а не домашним.
3. Настройки → Подключение → *Сервис проверки IP*: выберите другой сервис и повторите проверку.
4. Отключитесь — карточка результата исчезает. В Mock-режиме кнопка отключена и показывает пояснение.
5. При ошибке сети или сервиса показывается понятный совет без технических подробностей.

## 9. Первый запуск и пустое состояние

1. Запустите с отдельным пустым каталогом данных (реальные настройки не затрагиваются):
   `$env:BYDLO_DATA_DIR = Join-Path (Get-Location) '.tmp/first-run'` и затем
   `dotnet run --project src/Bydlo.Desktop -- --mock`.
2. Должен появиться экран приветствия с выбором языка и темы. По умолчанию выбраны язык системы и системная тема.
3. Смените язык и тему, нажмите «Начать» (или «Пропустить»). Настройки применяются сразу.
4. Пока серверов нет, главная показывает приветствие и три карточки: «Ссылка или подписка», «Файл», «QR-код».
   Проверьте каждую: вставка ссылки, выбор файла и выбор изображения с QR-кодом.
5. После добавления сервера пустое состояние исчезает и появляется обычная кнопка подключения.
6. Перезапустите BYDLO с тем же `BYDLO_DATA_DIR` — экран приветствия больше не показывается.

## Отчёт об ошибке

Укажите ОС и её версию, версию BYDLO, движок и его версию, протокол, режим (прокси/TUN) и очищенный лог.

## Kill switch (#16)

Изолированные тесты `KillSwitchTests` проверяют конфигурацию IPv4/IPv6, независимость
исключений LAN/mesh, отсутствие прямого fallback, сохранение TUN при неудачных повторах,
снятие блокировки при ошибке запуска/остановки и поведение при сбое самого TUN.
Процессы и реальные сетевые интерфейсы в них не запускаются.

Мейнтейнер вручную, на отдельной тестовой машине с восстановлением доступа, проверяет:

- Предупреждение, подтверждение включения и применение после переподключения TUN.
- Отказ транспорта, все попытки переподключения и отключённый AutoReconnect:
  публичные IPv4/IPv6/DNS не выходят напрямую, выбранные LAN/mesh доступны.
- Восстановление транспорта без пересоздания TUN и без прямого интернет-доступа в паузе.
- Обычное отключение, аварийную кнопку, закрытие окна и завершение приложения:
  TUN и его временные маршруты/фильтры снимаются.
- Сбой BYDLO при работающем TUN, следующий запуск и восстановление с теми же правами;
  чужие VPN/mesh не завершаются. Отказ в доступе не удаляет запись из журнала.
- Собственное падение TUN: интерфейс показывает ошибку; это явно описанное ограничение защиты.

Автоматически эти сетевые сценарии не выполнять.

## Восстановление после ошибки остановки (#37)

`EngineCleanupTests` используют только fake runner и временные файлы. Они проверяют остановку процесса
при ошибке очистки firewall, сохранение ссылки после ошибки остановки/Dispose, повторную остановку,
ошибку очистки после неудачного запуска и завершение остальных инструментов при ошибке одной сессии.
При незавершённой очистке сессия остаётся в состоянии ошибки с доступной кнопкой остановки.

В отчётах наподобие #36 указывайте ОС, версию приложения, выбранную стратегию Zapret,
режим Game Filter, режим основного подключения и очищенный журнал до и после остановки.
Игровой фильтр может затрагивать порты 1024–65535; без настроек и журнала нельзя установить,
почему конкретная игра не подключилась или сохранилась ли проблема после завершения winws.
Автоматические тесты не подтверждают совместимость стратегии с Dota 2 и не меняют сетевые настройки.

## Передача сервера (#17)

`ExportTests` проверяют импорт → экспорт → импорт ссылок всех поддерживаемых форматов,
IPv6, Unicode, спецсимволы, транспорт/TLS/REALITY, port hopping, obfs и данные доступа.
Для WireGuard/AmneziaWG/OpenVPN проверяются сохранение исходного конфига, ключей,
нескольких пиров и встроенных сертификатов, а также отказ при отсутствии секретов.

Безопасная headless-проверка меню, подтверждения предупреждения, QR и буфера обмена:

```powershell
. ./scripts/env.ps1
dotnet run --project tools/Bydlo.Screenshots -c Release -- .tmp/share-verification en --verify-share
```

Проверка использует фиктивные данные и отдельный каталог appdata, не запускает движки.
Результаты: `share-menu.png`, `share-warning.png`, `share-qr.png`.
Для ручной проверки экспорта в Mock Mode импортируйте тестовый `.conf` / `.ovpn`,
в меню сервера выберите экспорт, подтвердите предупреждение и укажите файл.
Проверьте расширение, повторный импорт и отмену диалога без записи файла.
## Автоподбор Zapret

В «Инструменты → Zapret» кнопка «Подобрать лучший конфиг» запускает асинхронную проверку
всех обнаруженных BAT-конфигураций Windows или нативных пресетов Linux/macOS. Запуск только
явный, с предупреждением; нужны права администратора/root и curl с поддержкой HTTP/TLS.
В Mock-режиме и при `BYDLO_SAFE_DEV=1` реальные проверки запрещены; результаты не имитируются.
Адреса редактируются: от 1 до 20 HTTP(S)-URL без учётных данных, query и fragment.

Использован управляемый перенос **стандартной HTTP/TLS-части Test Zapret 1.10.3**:
[исходник Flowseal](https://github.com/Flowseal/zapret-discord-youtube/blob/1.10.3/utils/test%20zapret.ps1).
На Windows проверяется наличие исходного Test Zapret в установленном пакете. Его интерактивный
координатор не исполняется: он сам перебирает BAT-файлы, меняет ipset и завершает все winws
по имени, поэтому для встраивания в приложение не подходит. Вместо повторного вложенного
перебора BYDLO один раз управляет собственным циклом, запускает winws через существующий
парсер BAT и ConnectionManager, а curl выполняет HTTP/1.1, TLS 1.2 и TLS 1.3 HEAD-проверки.
BAT-файл в отчёте однозначно обозначает извлечённые из него аргументы winws, а не исполнение
всех команд BAT. Для Linux/macOS проверяются отдельные нативные пресеты, а не Windows BAT.

Не включены ping, DPI TCP 16–20, UDP/QUIC, голос Discord и воспроизведение видео. Доступность
главной страницы сервиса не доказывает работу этих функций. Проверки идут напрямую, без
переменных HTTP-прокси и пользовательского curlrc; действующий системный VPN может влиять
на результат, его BYDLO не перенастраивает. Сертификаты проверяются. Успех требует exit code 0
и HTTP 200–399; быстрые ошибки не засчитываются. Exit 28 — таймаут, неподдерживаемый TLS и
неизвестный/неполный формат — отдельный неизвестный результат. Время берётся из curl
`time_total` только для успешных проверок.

Каждая конфигурация проверяется дважды. Сравниваются число успехов в худшем повторе,
общее число успехов, среднее время успешных ответов; при полном равенстве предпочтителен
исходный конфиг. Нестабильный вариант без успехов в одном из повторов не рекомендуется.
После каждого повтора собственный процесс останавливается. Ошибка очистки прерывает весь
подбор. Есть таймаут запуска (15 с), каждого curl (4 с плюс ограничение процесса 6 с),
всего набора проверок (100 с); не более четырёх curl одновременно.

ConnectionManager удерживает блокировку жизненного цикла до конца восстановления, поэтому
параллельные подборы запрещены. До применения возвращается именно исходная активная сессия,
а если Zapret был остановлен — остаётся остановленным. Отмена и ошибки также проходят
восстановление без отменённого токена. Чужие процессы не завершаются. При неудаче восстановления
приложение явно сообщает об этом и запрещает применение рекомендации.

«Применить рекомендацию» повторно запускает выбранный вариант, проверяет запуск и сохраняет
настройки; ошибка запуска или записи настроек вызывает откат. Автоприменения нет. Последний
отчёт с датой, URL, исходным/рекомендованным/применённым вариантом, всеми результатами и
диагностикой атомарно сохраняется в `zapret-selection.json` каталога данных BYDLO. После
перезапуска он доступен для просмотра; применение требует нового подбора. Новое нажатие
всегда запускает новую проверку. После изменения настроек прежнюю рекомендацию применять нельзя.

Безопасная проверка разработчиком:

```powershell
. ./scripts/env.ps1
./scripts/check.ps1
dotnet run --project tools/Bydlo.Screenshots -c Release -- .tmp/selection-ui ru --verify-zapret-selection
```

Модульные тесты используют фейковые сессии/проверки/процессы: ранжирование, кириллица в именах,
ошибки HTTP, отсутствие успешных вариантов, неполный формат, отмена, таймауты запуска и
проверок, сбой процесса, ошибки очистки/восстановления, откат применения и ошибка сохранения.
Headless-проверка загружает тестовый отчёт, рендерит широкий/узкий интерфейс и проверяет
отказ запуска в Mock-режиме. Реальная эффективность, права драйвера и восстановление на
конкретном подключении проверяются владельцем вручную; разработчик и CI сетевые тесты не запускают.

### Проверка сохранённой стратегии при запуске (#49)

При первом открытии «Инструменты» за сеанс приложение один раз проверяет только
запомненную стратегию (`Settings.Zapret.Strategy`) тем же HTTP/TLS-набором.
Остальные стратегии не запускаются, автоприменения нет. Статус виден под
выбором стратегии: проверка выполняется / работает / частично / не работает /
проверить не удалось, подробности — в раскрывающемся блоке по адресам и протоколам.

Вручную (только владелец, с правами администратора/root, вне Mock/Safe Dev):
применить стратегию, перезапустить приложение, открыть «Инструменты» — должна
пройти проверка именно этой стратегии; отчёт подбора при этом не перезаписывается.
Граничные случаи: сохранённой стратегии нет (явное сообщение, подбора нет),
стратегия пропала из установки (недоступна), Zapret уже запущен (автопроверка
пропускается, доступна кнопка «Проверить снова»), Mock/Safe Dev и отсутствие
прав (пропуск с объяснением, без запуска движка).

### Перезапуск с правами из «Инструментов» (#34, только Windows)

Приложение всегда стартует без повышения прав (`asInvoker`). Если запуск Zapret
упал с `error.engine.zapret.admin`, в карточке Zapret рядом с ошибкой появляется
кнопка «Перезапустить от администратора» (только Windows вне повышения:
`PrivilegeService.CanRestartElevated` сейчас умеет только `runas`).
Вручную: без прав включить Zapret → ошибка + кнопка → перезапуск через UAC →
повторный запуск Zapret идёт уже без ошибки прав.
На Linux/macOS механизма запроса повышения из приложения пока нет — там действует
только понятное сообщение об ошибке; задачу #34 целиком этот PR не закрывает.

## Трей, автозапуск и уведомления (#15)

В «Настройки → Работа в фоне» независимо включаются автозапуск при входе, подключение
к выбранному серверу при старте, сворачивание при закрытии и системные уведомления.
Первые три опции по умолчанию выключены; уведомления включены. Подключение не запускается
до завершения первого знакомства или без профилей. Автозапуск не повышает права: для TUN
и других привилегированных режимов по-прежнему нужны соответствующие права.

Автозапуск регистрируется только явным переключением, для текущего пользователя:
HKCU Run / `bydlo.desktop` в XDG autostart / `org.bydlo.desktop.plist` в LaunchAgents.
Нужен apphost или опубликованный исполняемый файл, запущенный из постоянной папки.
После перемещения приложения выключите и включите опцию заново. На macOS регистрация
срабатывает при следующем входе, служба немедленно не загружается. Аргумент `--autostart`
скрывает окно только при включённом сворачивании в трей и наличии реализации трея.

Иконка меняет состояние с учётом VPN и обоих инструментов; меню позволяет открыть окно,
подключиться/отключиться, выбрать сервер для следующего подключения, переключить Zapret
и TgWsProxy, выйти. Выход ожидает остановки всех сессий. При ошибке очистки окно открывается
с предложением повторить выход. Linux DE должен поддерживать StatusNotifierItem/AppIndicator;
в GNOME может требоваться расширение. Если реализация трея отсутствует, окно при закрытии
завершает приложение. В macOS окно открывается через пункт меню, поскольку клик TrayIcon
там не вызывает событие Avalonia. Выбор сервера сам по себе не переключает активный туннель.

Уведомления: потеря соединения при переподключении, восстановление и ошибка движка.
Обновления трафика и обычное отключение уведомлений не создают. Диагностика и реквизиты
сервера в системную историю не передаются. Windows использует Shell balloon с временной
иконкой на время уведомления; Linux требует `notify-send` и демон уведомлений;
macOS использует системный `osascript` (разрешения и режим «Не беспокоить» влияют на показ).
Отсутствие уведомлений не прерывает соединение; отказ записывается в журнал.

Безопасные проверки разработчика, без регистрации в ОС и реальных движков:

```powershell
. ./scripts/env.ps1
./scripts/check.ps1
dotnet run --project tools/Bydlo.Screenshots -c Release -- .tmp/desktop-ui ru --verify-desktop
```

`DesktopIntegrationTests` проверяют настройки, параллельное сохранение, переходы уведомлений,
раздельность сессий и экранирование регистраций. Headless-проверка использует только MockEngine:
подключение при старте, меню/состояние трея, отключение, настройки, запрет регистрации
при safety lock, выход и рендер широкого/узкого окна. Обычный CI на GitHub выполняет её на Ubuntu и Windows, зеркало на Gitea — только на Linux x64. macOS проверяется по тегу релиза или вручную; схема описана в [BUILD.md](BUILD.md#ci).

### Проверка упаковки без запуска движков

Для AmneziaWG на macOS `MacAmneziaNetworkTests` проверяет команды IPv4/IPv6,
прямой маршрут к серверу, восстановление DNS (в том числе автоматического через `Empty`),
сохранение чужих изменений, повтор после сбоя и исключительное владение журналом.
`BundledEngineTests` проверяет передачу имени utun от фиктивного хоста, удаление устаревшего
файла имени и очистку при отсутствии нового имени. Все процессы и сетевые команды — фейки;
защитный режим проверяется отдельно, реальные интерфейсы не создаются.
В каждом CI AmneziaWG дополнительно компилируется для `darwin/arm64`, проверяется заголовок
Mach-O и публикуется SHA-256 хоста. Полный комплект macOS с исходниками и лицензиями
проверяется на Apple Silicon по тегу или через `workflow_dispatch`, без исполнения движков.

```powershell
. ./scripts/env.ps1
./scripts/test-engine-bundle.ps1
```

Проверка создаёт синтетические файлы внутри `.tmp/` и проверяет отклонение неверной архитектуры,
формата или ARM64-среза Mach-O, отсутствующих движков, исходников и лицензий, несовпадающих хешей,
пустого/неполного манифеста и повреждённого кеша OpenVPN. Частичный macOS-комплект обязан провалить
полную релизную проверку. На GitHub этот тест запускается на Ubuntu и Windows в обычном CI.
Safety lock также подавляет доставку системных уведомлений.

Ручная проверка владельцем на каждой ОС: включить/отключить автозапуск в опубликованной
сборке и проверить следующий вход в систему; проверить возврат из трея, изменение
состояния при работе инструментов, завершение через «Выход», обычное закрытие с опцией
сворачивания и без неё. Для уведомлений можно использовать явный `--mock` без safety lock
и сценарий DropAfterConnect; проверить потерю/восстановление, FailOnConnect, выключение
уведомлений и режим «Не беспокоить». Агенты не выполняют нативную регистрацию и не запускают
реальные сетевые сценарии. Нативная доставка, поведение оболочек Linux и вход в систему
не подтверждены headless-тестами.

## Регрессионные проверки PR #96

`ConfigImportTests` проверяет типы секций JSON и ссылки на исходящие подключения;
`BackupSettingsValidationTests` — новые поля DNS/DPI и совместимость со старыми копиями;
`ChainTests` — ограничения готовых режимов при явном выборе движка;
`ServerSpeedTests` — отмену и повторную очистку временных движков с фейковым запуском.
Для #79 дополнительно проверяются ограничение загрузки 4 МиБ, заголовки запрета кеширования
и сжатия, частичный результат при истечении времени загрузки, отмена во время чтения,
отклонение некорректных URL до запуска, ограничение параллельности и ожидание очистки
всех активных измерений при отмене пакета. Ошибка очистки не должна превращаться в нулевую скорость.
HTTP подменён обработчиком и потоками в памяти; процессы — `FakeProcessRunner`.
Интерфейс #79 проверяется командой `dotnet run --project tools/Bydlo.Screenshots -c Release -- .tmp/speed-verification ru --verify-speed --mock`
после загрузки `scripts/env.*`: сортировка, сохранение выбора, отображение результата «—»,
блокировка замеров в безопасной сессии с пояснением и привязки на ширине 1180 и 380 пикселей.
Снимки содержат синтетические результаты, полученные без сети и движков.

## Простой интерфейс (#92)

```powershell
. ./scripts/env.ps1
dotnet run --project tools/Bydlo.Screenshots -c Release -- .tmp/simple-ui-review ru --mock --verify-simple-ui
```

Используйте новый каталог вывода: сценарий проверяет пустую главную до добавления
демонстрационных серверов. Данные изолированы в `<каталог вывода>/appdata`.
Сценарий снимает Purple, Light, OLED и System при ширине 1180, 900, 760 и 380 пикселей,
проверяет переходы в импорт ссылки/подписки, файла, QR и буфера, сохранность открытого
черновика, раскрытие и сохранение расширенных настроек, доступность инструментов без
серверов и отдельное переключение Mock-движков. Нативные диалоги и содержимое системного
буфера здесь не проверяются: проверяется корректная страница мастера при недоступном сервисе.
Реальные движки и сетевые настройки не используются.

Проверка `--verify-active-connections` открывает «Настройки → Дополнительно» в `--mock`:
список, поиск по домену/процессу/правилу/исходящему, закрытие и заполнение редактора правил.

закрытия, fallback на IP и путь процесса, ошибки API/JSON и недопустимые ID.
